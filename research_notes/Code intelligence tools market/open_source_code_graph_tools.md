# Open-source and self-hostable code intelligence and code-graph tools for coding agents (November 2026)

Source-quality note for the report writer:
- Items marked **[verified 2026-11]** were checked against a live page during this research session.
- Items marked **[repo docs, not re-verified]** come from the project's primary repository or documentation as known up to mid-2026, cited to the primary URL, and should be spot-checked before publication because star counts, licences and release dates move quickly.
- Star counts are approximate and dated where a date was available.

## Which tools are actively maintained in late 2026 and which are abandoned?

### Takeaway
The indexing-format layer has consolidated around tree-sitter (syntax) plus LSP and SCIP (semantics), while GitHub's Stack Graphs (archived September 2025), LSIF (superseded by SCIP since 2022) and the Kuzu embedded graph database (archived October 2025, continued as the LadybugDB fork) are no longer viable foundations. Among agent-facing tools, Serena, GitNexus, claude-context, ast-grep and the codebase-memory family are clearly active in late 2026, but the field is crowded with young single-maintainer MCP servers whose longevity is unproven.

### Cited Findings

#### Indexing formats and standards
- **SCIP (Source Code Intelligence Protocol)** is a Protobuf-based index format that Sourcegraph introduced in 2022 as a replacement for LSIF, with indexers such as scip-typescript (TypeScript and JavaScript) and scip-java (Java, Scala and Kotlin). — [Sourcegraph: Announcing SCIP](https://sourcegraph.com/blog/announcing-scip)
- scip-java continued to ship releases in 2026, with versions 0.12.0 (2026-03-24), 0.12.1 (2026-04-01) and 0.12.3 (2026-04-02) on Maven Central; no later release was found in this session. — [Maven Central scip-java 0.12.3](https://repo1.maven.org/maven2/com/sourcegraph/scip-java_2.13/0.12.3) **[verified 2026-11]**
- The status of scip-python could not be confirmed for 2026; the only search hit was a third-party fork of the pyright-based indexer. — [codean-io/scip-python](https://github.com/codean-io/scip-python)
- A secondary news source reports that SCIP moved to independent open governance with a steering committee including Meta and Uber engineers; this could not be confirmed from a primary source. — [lavx news (secondary)](https://news.lavx.hu/article/scip-protocol-transitions-to-independent-open-governance-with-meta-and-uber-steering-committee)
- SCIP indexers are compiler-driven, so they generally require a working build (dependencies resolved, project compiles) to emit precise definitions and references. — [Sourcegraph: Announcing SCIP](https://sourcegraph.com/blog/announcing-scip) **[repo docs, not re-verified]**
- **LSIF** is the older Microsoft/Sourcegraph JSON-lines format that SCIP was designed to replace, and Sourcegraph described SCIP as "a better code indexing format than LSIF" in 2022. — [Sourcegraph: Announcing SCIP](https://sourcegraph.com/blog/announcing-scip)
- **Stack Graphs** (GitHub's name-resolution framework built on tree-sitter, used for precise code navigation on github.com) was archived by its owner on 9 September 2025 and is read-only. — [Archived snapshot of github/stack-graphs](https://proxy-ga.blitzz.co/proxy/123456/web.archive.org/web/20260601045401/https:/github.com/github/stack-graphs) **[verified 2026-11]**
- **Kythe** is Google's open-source cross-reference indexing ecosystem with indexers for C++, Java, Go, TypeScript and Protocol Buffers, storing a graph of nodes and edges for code navigation. — [kythe.io](https://kythe.io/) **[repo docs, not re-verified]**
- **Glean** is Meta's open-source system for collecting, deriving and querying facts about source code, open-sourced in August 2021 and described in a December 2024 Meta engineering post. — [Meta Engineering: Indexing code at scale with Glean (2024-12-19)](https://engineering.fb.com/2024/12/19/developer-tools/glean-open-source-code-indexing/)
- Glean ingests SCIP indexes for Rust (via rust-analyzer), Go, TypeScript, Java, Python and .NET, but its README notes that some of Meta's custom indexers are not part of the open-source release. — [Glean README on Hackage](https://hackage.haskell.org/package/glean-0.1.0.0/src/README.md)
- **tree-sitter** is an incremental parser generator that produces concrete syntax trees for hundreds of languages and is the parsing layer under most agent-facing code graphs (Aider, GitNexus, Codanna, CodeGraphContext, codebase-memory, ast-grep). — [tree-sitter documentation](https://tree-sitter.github.io/tree-sitter/) **[repo docs, not re-verified]**
- **Language Server Protocol** servers provide on-demand definitions, references, implementations, rename and diagnostics, and they are the semantic backend of Serena, multilspy and mcp-language-server. — [LSP specification](https://microsoft.github.io/language-server-protocol/) **[repo docs, not re-verified]**

#### Agent-facing semantic tools
- **Serena (Oraios AI)** is an MCP server providing symbol-level retrieval and editing (find symbol, symbol overview, find referencing symbols, find declaration, find implementations, diagnostics, replace symbol body, insert before/after symbol, rename) over language servers for more than 40 languages, with an optional paid JetBrains plugin backend. — [oraios/serena](https://github.com/oraios/serena) **[verified 2026-11]**
- Serena had about 31.3k stars and 2.1k forks in November 2026, and its README announces "Serena v2 with the new REPL-based agent interface". — [oraios/serena](https://github.com/oraios/serena) **[verified 2026-11]**
- Serena's licence changed with v2: the SolidLSP component remains MIT while the Serena application is GPL-3.0-or-later, and combined distributions fall under the GPL. A secondary source dates v2.0.0 to 13 October 2026 and v2.1.0 to 19 October 2026. — [oraios/serena](https://github.com/oraios/serena) **[verified 2026-11]**; [issoh.co.jp article (secondary, dates)](https://www.issoh.co.jp/md/tech/8197)
- Many directory sites still describe Serena as MIT-licensed, which is stale after the v2 change. — [Kumanyaev comparison, June 2026](https://zzet.org/gortex/local-code-graph-mcp-servers-compared/)
- Serena's own stated limitations with the free LSP backend are that find-declaration generally fails for symbols in external dependencies, find-implementations depends on the language server, rename covers only symbols, and move/inline/propagate-deletion require the paid JetBrains plugin. — [oraios/serena](https://github.com/oraios/serena) **[verified 2026-11]**
- **multilspy** is Microsoft Research's Python library that launches and talks to language servers, originally built for the "monitor-guided decoding" work, and Serena's SolidLSP layer descends from it. — [microsoft/multilspy](https://github.com/microsoft/multilspy) **[repo docs, not re-verified]**
- **mcp-language-server** is a Go MCP server that exposes definition, references, diagnostics, hover and rename from any stdio language server (gopls, pyright, typescript-language-server, rust-analyzer, clangd). — [isaacphi/mcp-language-server](https://github.com/isaacphi/mcp-language-server) **[repo docs, not re-verified]**
- **Aider repo map** builds a graph of definitions and references with tree-sitter, ranks symbols with a PageRank-style algorithm, and sends a token-budgeted map (default about 1k tokens, configurable with `--map-tokens`) to the model. — [Aider: Repository map](https://aider.chat/docs/repomap.html) **[repo docs, not re-verified]**
- **Cline** deliberately does not index codebases; its blog argues that chunking code for embeddings breaks code logic and that keeping an index fresh requires a continuous pipeline. — [Cline blog: Why Cline doesn't index your codebase](https://cline.bot/blog/why-cline-doesnt-index-your-codebase-and-why-thats-a-good-thing)
- **Claude Code** moved away from RAG with a local vector database to agentic grep/glob search; Boris Cherny is quoted as saying "Early versions of Claude Code used RAG + a local vector DB, but we found pretty quickly that agentic search generally works". — [Morph: codebase indexing (secondary quote)](https://morphllm.com/codebase-indexing)
- **Roo Code** (a Cline fork) added optional codebase indexing using tree-sitter chunking, an embedding provider (OpenAI-compatible or Ollama) and a Qdrant vector store. — [Roo Code docs: Codebase Indexing](https://docs.roocode.com/features/codebase-indexing) **[repo docs, not re-verified]**
- **Continue** has historically indexed locally with embeddings stored in LanceDB plus SQLite full-text search for its `@codebase` context provider; its current status in late 2026 was not verified. — [Continue docs](https://docs.continue.dev/) **[repo docs, not re-verified]**
- **OpenHands** (MIT) relies on shell tools (grep, find) and a file editor inside a sandbox rather than a persistent code index. — [All-Hands-AI/OpenHands](https://github.com/All-Hands-AI/OpenHands) **[repo docs, not re-verified]**
- **claude-context (Zilliz)** is an MCP server that chunks and embeds a codebase into Milvus or Zilliz Cloud, exposes hybrid BM25 plus vector search, and uses Merkle trees for incremental re-indexing; it is MIT-licensed with roughly 10.9k stars (undated roundup). — [zilliztech/claude-context](https://github.com/zilliztech/claude-context); [computingforgeeks roundup](https://computingforgeeks.com/reduce-claude-code-token-usage-tools/)
- claude-context's README claims about 40% token reduction at equivalent retrieval quality, and a third-party evaluation reproduced 39.4% against a grep-only baseline on the older 0.1.0 release. — [zilliztech/claude-context](https://github.com/zilliztech/claude-context); [claude-context evaluation README](https://glama.ai/mcp/servers/@zilliztech/claude-context/blob/2484ae29b3a9c92815f1524cbb9924b3e241ec17/evaluation/README.md)
- **codebase-memory (codebase-memory-mcp)** builds a persistent tree-sitter knowledge graph for 66 languages and exposes it over MCP; it is described in a March 2026 arXiv preprint by Vogel et al. — [arXiv 2603.27277 (2026-03-28)](https://arxiv.org/abs/2603.27277) **[verified 2026-11]**
- **GitNexus** (abhigyanpatwari/GitNexus) indexes a repository into a knowledge graph using tree-sitter for 12 languages, stores it in KuzuDB, and is exposed as an MCP server (`npx gitnexus mcp`), a CLI (`analyze`, `wiki`, `setup`, `clean`) and a serverless browser UI; npm releases reached at least 1.6.9 in 2026. — [GitNexus README (npm 1.6.9)](https://cdn.jsdelivr.net/npm/gitnexus@1.6.9/README.md); [GitNexus docs: knowledge graph](https://www.mintlify.com/abhigyanpatwari/GitNexus/concepts/knowledge-graph)
- GitNexus star counts conflict between sources (about 33k on SourcePulse and about 45k cited on Product Hunt), and the project has known gaps in Swift ingestion. — [SourcePulse](https://www.sourcepulse.org/projects/22555251); [Product Hunt](https://www.producthunt.com/posts/1232678)
- GitNexus depends on KuzuDB, which was archived in October 2025, which creates a storage-layer maintenance risk unless it migrates to a fork. — [OneUptime: Kuzu was archived (2026-08-12)](https://oneuptime.com/blog/post/2026-08-12-kuzu-archived-pin-0-11-3-fork-or-migrate/markdown)
- **Codanna** is a Rust, Apache-2.0, local-first, read-only code graph using tree-sitter with call graphs, implementations and type relationships plus local embeddings (FastEmbed all-MiniLM-L6-v2); it claimed indexing over 75,000 symbols per second and had 687 stars on 2026-06-06. — [Kumanyaev comparison (2026-06-06)](https://zzet.org/gortex/local-code-graph-mcp-servers-compared/)
- **CodeGraphContext** writes a tree-sitter graph (optionally enriched with SCIP definitions and references) into a graph database, defaulting to FalkorDB Lite with Kuzu, LadybugDB and Neo4j as alternatives. — [repowise comparison](https://repowise.dev/blog/comparisons/best-code-graph-mcp-servers); [ChatForest review](https://chatforest.com/reviews/code-intelligence-codebase-graph-mcp-servers/)
- A vendor-run benchmark found that CodeGraphContext's incremental updates missed up to 474 edges that a fresh build found, more than the other tools tested; the benchmark author's own tool was among those compared. — [PipesHub: How accurate is your code graph?](https://pipeshub.com/blog/code-graph-benchmark)
- **Gortex** is a Go, Apache-2.0 graph plus hybrid retrieval server (BM25, vectors and graph reranking) claiming 257 languages in three parsing tiers; its own author wrote the comparison that describes it. — [Kumanyaev comparison (2026-06-06)](https://zzet.org/gortex/local-code-graph-mcp-servers-compared/)
- **ChunkHound** is an MIT embeddings tool with AST-aware chunking (cAST) and regex search, with no structural graph; its paper reports +4.3 recall on RepoEval and +2.67 pass@1 on SWE-bench versus naive chunking. — [Kumanyaev comparison (2026-06-06)](https://zzet.org/gortex/local-code-graph-mcp-servers-compared/)
- **code-graph-rag** (vitali87) parses repositories with tree-sitter into a Memgraph knowledge graph and answers natural-language questions by generating Cypher. — [vitali87/code-graph-rag](https://github.com/vitali87/code-graph-rag) **[repo docs, not re-verified]**
- **Blarify** (Blar) builds a code graph from tree-sitter plus language-server references into Neo4j or FalkorDB for languages including Python, JavaScript, TypeScript, Ruby, Go and C#. — [blarApp/blarify](https://github.com/blarApp/blarify) **[repo docs, not re-verified]**
- **Potpie** (Apache-2.0) builds a Neo4j knowledge graph of a codebase and runs prebuilt and custom agents (debugging, test generation, Q&A) over it. — [potpie-ai/potpie](https://github.com/potpie-ai/potpie) **[repo docs, not re-verified]**
- **ast-grep** is a Rust, MIT, tree-sitter-based structural search, lint and rewrite CLI with pattern syntax that resembles code, and it has an MCP server. — [ast-grep/ast-grep](https://github.com/ast-grep/ast-grep); [ast-grep/ast-grep-mcp](https://github.com/ast-grep/ast-grep-mcp) **[repo docs, not re-verified]**
- **Probe** (Probe Labs) combines ripgrep-speed search with tree-sitter to return whole functions or classes rather than lines, without a persistent index, and ships a CLI and MCP server. — [probelabs/probe](https://github.com/probelabs/probe) **[repo docs, not re-verified]**
- Comparison authors agree that there is no single best local code-graph MCP server because the tools use four different index paradigms (LSP live queries, precomputed graphs, embeddings, and hybrids). — [Kumanyaev comparison](https://zzet.org/gortex/local-code-graph-mcp-servers-compared/)

#### Code-as-database and analysis engines
- **CodeQL** extracts a relational database (ASTs, data flow, control flow, types) from a build and queries it with the QL language, while **Joern** stores a code property graph (AST plus control flow plus program dependence) in an in-memory graph. — [Joern vs CodeQL comparison](https://elmanto.github.io/posts/sast_derby_joern_vs_codeql)
- CodeQL supports C/C++, C#, Go, Java/Kotlin, JavaScript/TypeScript, Python, Ruby, Swift and GitHub Actions (with Rust added in 2025), and it does not support COBOL or SQL. Its licence permits free use on open-source code and research but requires GitHub Advanced Security for private commercial code. — [CodeQL supported languages](https://codeql.github.com/docs/codeql-overview/supported-languages-and-frameworks/); [GitHub CodeQL CLI licence](https://github.com/github/codeql-cli-binaries/blob/main/LICENSE.md) **[repo docs, not re-verified]**
- Joern (Apache-2.0) has frontends for C/C++, Java and JVM bytecode, JavaScript/TypeScript, Python, Kotlin, PHP, Go, Ruby, Swift and C#, and no COBOL frontend was found. — [joern.io](https://joern.io/); [Joern docs: frontends](https://docs.joern.io/frontends/) **[repo docs, not re-verified]**
- **Semgrep** is a pattern-based multi-language static analyser; in December 2024/January 2025 Semgrep changed the licence of its maintained rules and moved some engine features out of the open-source edition, which prompted the LGPL **Opengrep** fork by a consortium of security vendors. — [Opengrep announcement](https://www.opengrep.dev/) **[repo docs, not re-verified]**
- **OpenRewrite** represents code as Lossless Semantic Trees (type-attributed, format-preserving ASTs) for deterministic large-scale refactoring recipes, with strongest support for Java and the JVM and newer support for JavaScript/TypeScript, Python and C# driven by Moderne. — [OpenRewrite docs: Lossless Semantic Trees](https://docs.openrewrite.org/concepts-and-explanations/lossless-semantic-trees) **[repo docs, not re-verified]**

#### Graph stores
- **Kuzu** was archived on 10 October 2025 with v0.11.3 as its last release, reportedly after its company was acquired (by Apple, per secondary sources only). — [OneUptime: Kuzu was archived (2026-08-12)](https://oneuptime.com/blog/post/2026-08-12-kuzu-archived-pin-0-11-3-fork-or-migrate/markdown)
- **LadybugDB** is the MIT community fork that describes itself as "the database formerly known as Kuzu"; it has no corporate backing or commercial support, renames the Python package (`import ladybug`) and file extension (`.lbdb`), and requires a logical export from Kuzu 0.11.3 rather than a file rename. — [OneUptime: Kuzu to LadybugDB (2026-08-12)](https://oneuptime.com/blog/post/2026-08-12-kuzu-to-ladybugdb-packages-apis-extensions-database-files/markdown); [LadybugDB site](https://ladybugdb-web.pages.dev/)
- **FalkorDB** (a Redis-module graph database, successor to RedisGraph) publishes a reference "code-graph" project that builds and visualises code knowledge graphs, and FalkorDB Lite is the default store for CodeGraphContext. — [FalkorDB/code-graph](https://github.com/FalkorDB/code-graph) **[repo docs, not re-verified]**; [repowise comparison](https://repowise.dev/blog/comparisons/best-code-graph-mcp-servers)
- **Neo4j** Community Edition is GPLv3 and limited to a single instance, while clustering and hot backups are in the commercial Enterprise Edition; Potpie, Blarify, CodexGraph and CodeGraphContext all support it. — [Neo4j licensing](https://neo4j.com/licensing/) **[repo docs, not re-verified]**
- **Memgraph** is the store used by code-graph-rag. — [vitali87/code-graph-rag](https://github.com/vitali87/code-graph-rag) **[repo docs, not re-verified]**

#### Scaling limits
- Building Joern's code property graph for a Linux-kernel-sized repository requires a lot of RAM, which can be prohibitive on constrained machines, because Joern holds the CPG in memory. — [arXiv 2603.24837: Bridging CPGs and LLMs](https://arxiv.org/html/2603.24837v1)
- On a project over 1.5 million lines, a research prototype (QVoG) reported CPG extraction in about 15 minutes against 19 minutes for CodeQL, with memory use much lower than Joern's. — [arXiv 2406.08098: Scalable Defect Detection via Traversal on Code Graph](https://arxiv.org/html/2406.08098v1)
- A practitioner comparison recommends CodeQL for whole-codebase analysis and Joern for smaller codebases or slices, noting that CodeQL requires compiling the project for compiled languages. — [Joern vs CodeQL comparison](https://elmanto.github.io/posts/sast_derby_joern_vs_codeql)
- Meta built Glean specifically for indexing a monorepo at Meta's scale, which makes it the strongest open-source evidence of multi-million-line indexing, though some production indexers are not open-sourced. — [Meta Engineering (2024-12-19)](https://engineering.fb.com/2024/12/19/developer-tools/glean-open-source-code-indexing/)
- An independent benchmark ran graph tools on Kubernetes (146k graph nodes) and VS Code (219k nodes), which is the largest public agent-facing graph test found; no public agent benchmark on a multi-million-line polyglot estate was found. — [nefayran/code-graph-vs-grep](https://github.com/nefayran/code-graph-vs-grep) **[verified 2026-11]**

### Inferences
- The safe long-term building blocks are tree-sitter, LSP servers, SCIP and (for Meta-scale fact stores) Glean; tools built on Stack Graphs or plain Kuzu carry inherited abandonment risk.
- Serena is the most mature LSP-based agent tool by adoption, but its GPL-3.0 relicensing in October 2026 matters for any organisation that wants to embed or redistribute it.
- Most graph MCP servers (GitNexus, Codanna, CodeGraphContext, Gortex, code-graph-rag, Blarify) are tree-sitter-based, which means their call and reference edges are heuristic name matches rather than compiler-resolved, and accuracy degrades on overloaded, dynamic or dependency-injected code.
- The agent-tool category is less than two years old and dominated by individual or small-team maintainers, so maintenance status should be re-checked at adoption time rather than assumed from star counts.

### Gaps
- Exact November 2026 star counts, maintainer counts and last-release dates for Codanna, CodeGraphContext, code-graph-rag, Blarify, Potpie, Probe, ast-grep, mcp-language-server, multilspy and Continue were not verified in this session.
- No primary source was found confirming the SCIP open-governance transition or the current status of scip-python and scip-dotnet.
- Whether GitNexus has migrated from KuzuDB to LadybugDB was not determined.
- The "CodeCompass" paper named in the brief was not located, so its findings are not included.

## What evidence exists that graph or symbol tools improve agent outcomes versus plain grep/agentic search?

### Takeaway
The evidence is mixed and mostly small-scale: graph and symbol tools reliably help localisation and structural questions (callers, call chains, impact), and help weaker models most, but independent benchmarks found that frontier models with plain grep and read match graph tools on accuracy and are often cheaper in tokens on repositories up to roughly 25k graph nodes. The strongest end-to-end SWE-bench evidence (RepoGraph, LocAgent) dates from 2024–2025 and was measured on weaker scaffolds than current agents.

### Cited Findings
- RepoGraph (ICLR 2025) is a plug-in repository-level graph that raised SWE-bench Lite resolve rates by an average relative 32.8% across four agent and procedural frameworks, and the gain came mainly from better file-level localisation with smaller line-level gains. — [arXiv 2410.14684](https://arxiv.org/abs/2410.14684)
- LocAgent (ACL 2025) builds a directed heterogeneous graph of files, classes and functions and gives the agent three graph tools, reaching up to 92.7% file-level localisation accuracy on SWE-bench Lite with a fine-tuned Qwen-2.5-Coder-Instruct-32B. — [arXiv 2503.09089](https://arxiv.org/html/2503.09089)
- A 2026 paper on engineering reliable coding agents argues that bounded graph operations (find definitions, list callers, follow imports) are easier to validate than free-form generated graph queries, and notes that LocAgent's traversal depends on a strong lexical entry point. — [arXiv 2608.13867](https://arxiv.org/pdf/2608.13867)
- The Codebase-Memory preprint (March 2026, 31 repositories) found its MCP graph agent reached 83% answer quality versus 92% for a grep-and-read file-exploration agent, while using about 10x fewer tokens and 2.1x fewer tool calls, and it matched or beat the explorer on graph-native queries in 19 of 31 languages. — [arXiv 2603.27277](https://arxiv.org/abs/2603.27277) **[verified 2026-11]**
- An independent 2026 benchmark of 252 headless Claude Code runs (codebase-memory-mcp 0.9.0, a lean wrapper, and built-in Read/Grep/Glob) found the graph did not make Claude Code cheaper on repositories up to 25k nodes; with Sonnet on the 25k-node dub repository, Read and Grep were cheaper on 11 of 12 questions (p = 0.034) at equal accuracy (22/24). — [nefayran/code-graph-vs-grep](https://github.com/nefayran/code-graph-vs-grep) **[verified 2026-11]**
- In the same benchmark, Haiku answered structural questions on dub correctly 12/12 with the graph versus 8/12 with Read and Grep, and on Kubernetes and VS Code the graph-to-grep token ratio for structural questions was 0.29 for Haiku, 0.74 for Sonnet and 0.97 for Opus, so the benefit shrank as model strength rose. — [nefayran/code-graph-vs-grep](https://github.com/nefayran/code-graph-vs-grep) **[verified 2026-11]**
- The same benchmark found that tool-definition overhead mattered: loading graph tool definitions without a routing rule cost 62k tokens versus 30k with a routing rule, and a raw graph server was always more expensive than a lean wrapper around it. — [nefayran/code-graph-vs-grep](https://github.com/nefayran/code-graph-vs-grep) **[verified 2026-11]**
- A 60-task benchmark by the author of the sverklo symbol-graph MCP server found that tuned grep beat his own server by 9 F1 points overall, while the graph still won on structural questions such as imports and symbol relationships. — [DEV Community: I benchmarked code retrieval on 60 tasks](https://dev.to/nike-17/i-benchmarked-code-retrieval-for-ai-coding-agents-on-60-tasks-f9h)
- A 2026 preliminary study, "Does a Language Server Save Tokens for Coding Agents?", reported an LSP-only configuration at 0.778 F1 with a 19% increase in tokens overall, but the largest F1 gain and a token reduction on the hono repository; it used a local SWE-bench-style harness rather than official images. — [ResearchGate preprint](https://www.researchgate.net/publication/412312362_Does_a_Language_Server_Save_Tokens_for_Coding_Agents_A_Measurement_Methodology_and_Preliminary_Study)
- Serena's project page reports an internal evaluation of about 20 routine tasks with and without Serena plus testimonials, but no formal benchmark numbers. — [oraios/serena](https://github.com/oraios/serena) **[verified 2026-11]**
- Vendor claims of 47% to 98% token savings for graph MCP servers have not been independently reproduced. — [aibuilderclub guide](https://www.aibuilderclub.com/blog/codebase-memory-mcp-guide)
- Embedding search (claude-context) reports about 40% token savings versus grep-only retrieval, reproduced at 39.4% by a third party on an older release; the original claim comes from a vector-database vendor. — [Zilliz blog](https://zilliz.com/blog/why-im-against-claude-codes-grep-only-retrieval-it-just-burns-too-many-tokens); [evaluation README](https://glama.ai/mcp/servers/@zilliztech/claude-context/blob/2484ae29b3a9c92815f1524cbb9924b3e241ec17/evaluation/README.md)
- Anthropic's guidance, as reported secondhand, is to start with agentic search and add semantic search only if faster results or more variations are needed. — [jacar.es analysis (secondary)](https://jacar.es/en/code-agents-without-vector-search/)
- A claim that vector databases achieve only 45% recall on codebase search, attributed to a "CodeRAG-Bench 2026", could not be verified and should not be used. — [Fast.io article (unverified claim)](https://fast.io/resources/how-cline-reads-files-without-indexing/)
- CodexGraph (2024) connected LLM agents to a Neo4j code graph queried by generated Cypher and was evaluated on CrossCodeEval, SWE-bench Lite and EvoCodeBench, with Python as the only supported language. — [arXiv 2408.03910](https://arxiv.org/abs/2408.03910) **[repo docs, not re-verified]**
- CodeRAG (2025) retrieves supportive code over a requirement-to-code bigraph for repository-level code generation. — [arXiv 2504.10046](https://arxiv.org/abs/2504.10046) **[repo docs, not re-verified]**

### Inferences
- The pattern across sources is that structure helps localisation and "who calls this / what breaks if I change this" questions, while frontier models compensate with more grep turns, so the value of graph tools rises with repository size, model weakness and question structure, and falls with tool-definition overhead.
- No 2025–2026 study was found showing a statistically robust SWE-bench Verified or SWE-bench Pro resolve-rate gain from adding a graph or LSP MCP server to a frontier-model agent, so claims of outcome improvement should be framed as plausible but unproven at the frontier.
- Precise, bounded symbol operations (LSP- or SCIP-backed find-references, rename) are a more defensible investment than free-form graph-query tools because they are easier to validate and fail more transparently.
- Existing benchmarks use repositories far smaller than a multi-million-line enterprise estate, which is exactly where graph tools should help most, so the main evidential gap is at enterprise scale.

### Gaps
- No public head-to-head on SWE-bench Verified, SWE-bench Pro or a multilingual variant comparing the same frontier agent with and without a graph or LSP MCP server was found.
- No benchmark covering COBOL, C# or SQL-heavy repositories was found.
- Serena's internal evaluation methodology and results were not retrieved.

## What does it cost in engineering effort to run them on a large polyglot estate (Java, Python, TypeScript, C#, COBOL, SQL)?

### Takeaway
Syntax-level tools (tree-sitter graphs, ast-grep, Probe, embedding indexes) are cheap to stand up across languages but give heuristic edges, while precise tools (SCIP, LSP, CodeQL, OpenRewrite, Glean) require each project to build and therefore cost per-language build integration, CI capacity and memory. COBOL and SQL are the weak spot of the entire open-source ecosystem, and none of the agent-facing graph tools reviewed here supports them with semantic precision.

### Cited Findings
- SCIP indexers need a compilable project, with scip-java covering Java, Scala and Kotlin and scip-typescript covering TypeScript and JavaScript, so each repository needs build tooling in the indexing pipeline. — [Sourcegraph: Announcing SCIP](https://sourcegraph.com/blog/announcing-scip)
- CodeQL requires compiling the project for compiled languages, which makes setup harder than Joern's source-only frontends. — [Joern vs CodeQL comparison](https://elmanto.github.io/posts/sast_derby_joern_vs_codeql)
- Joern's in-memory CPG needs a lot of RAM on very large repositories. — [arXiv 2603.24837](https://arxiv.org/html/2603.24837v1)
- Serena with the LSP backend requires extra dependencies for some languages, and each language server it launches is a long-running process. — [oraios/serena](https://github.com/oraios/serena) **[verified 2026-11]**
- Glean's open-source release lacks some of Meta's custom indexers, so an adopter must supply SCIP indexers and operate the Glean server themselves. — [Glean README](https://hackage.haskell.org/package/glean-0.1.0.0/src/README.md)
- Tree-sitter-based graph servers can drift after code changes; one benchmark found CodeGraphContext's incremental update missed up to 474 edges compared with a full rebuild, which implies periodic full re-indexing. — [PipesHub benchmark](https://pipeshub.com/blog/code-graph-benchmark)
- Migrating a Kuzu-backed tool to LadybugDB requires a logical export and import plus API and package renames. — [OneUptime: Kuzu to LadybugDB](https://oneuptime.com/blog/post/2026-08-12-kuzu-to-ladybugdb-packages-apis-extensions-database-files/markdown)
- Tool-definition overhead of graph MCP servers can cost 30k to 62k tokens per session depending on how tools are loaded and routed, which is a recurring runtime cost. — [nefayran/code-graph-vs-grep](https://github.com/nefayran/code-graph-vs-grep) **[verified 2026-11]**
- For C#, scip-dotnet (Roslyn-based) exists and is referenced in Glean's documentation, though its current maintenance status was not confirmed. — [Glean README](https://hackage.haskell.org/package/glean-0.1.0.0/src/README.md)
- For COBOL, the main open-source building blocks are the Eclipse Che4z COBOL Language Support LSP server (Broadcom-contributed), the ProLeap ANTLR-based COBOL parser in Java, and community tree-sitter-cobol grammars; none is integrated into the agent-facing graph tools reviewed. — [eclipse-che4z/che-che4z-lsp-for-cobol](https://github.com/eclipse-che4z/che-che4z-lsp-for-cobol); [uwol/proleap-cobol-parser](https://github.com/uwol/proleap-cobol-parser); [yutaro-sakamoto/tree-sitter-cobol](https://github.com/yutaro-sakamoto/tree-sitter-cobol) **[repo docs, not re-verified]**
- Neither CodeQL nor Joern lists a COBOL frontend. — [CodeQL supported languages](https://codeql.github.com/docs/codeql-overview/supported-languages-and-frameworks/); [Joern frontends](https://docs.joern.io/frontends/) **[repo docs, not re-verified]**
- Recent COBOL research (2026) focuses on fixing LLM-generated COBOL compilation errors rather than on code graphs, which reflects the thin tooling base. — [arXiv 2604.03978: COBOLAssist](https://arxiv.org/pdf/2604.03978)

### Inferences
- A realistic open-source stack for a Java/Python/TypeScript/C# estate is SCIP indexers in CI (scip-java, scip-python, scip-typescript, scip-dotnet) feeding a queryable store, plus an LSP-based MCP server such as Serena for live edits, plus a tree-sitter or ast-grep layer for languages without a working build.
- The dominant engineering cost is not the graph database but making every repository build reproducibly in an indexing environment, which on a large estate is typically a dedicated platform-team effort measured in engineer-months rather than days (this is an estimate, not a sourced figure).
- COBOL (including copybooks, JCL and embedded SQL) and stand-alone SQL (stored procedures, cross-schema lineage) will need custom extraction, for example from the Che4z LSP or ProLeap parser into the same graph schema, so organisations with large mainframe estates should expect either commercial tooling or a bespoke pipeline.
- Cross-language edges (Java calling a stored procedure, TypeScript calling a C# API, COBOL calling DB2 tables) are not produced by any of the reviewed open-source tools and would have to be modelled separately.
- Single-host embedded stores (Kuzu/LadybugDB, FalkorDB Lite, LanceDB) suit per-repository indexes, while a cross-repository estate graph pushes towards a server store such as Neo4j Enterprise, Memgraph, FalkorDB server or Glean, with corresponding operational cost.

### Gaps
- No published engineer-hours, CI-minute or memory figures were found for SCIP, Glean or Serena deployments on a multi-million-line polyglot estate.
- No open-source tool was found that extracts SQL stored-procedure call graphs or COBOL program/copybook graphs into an agent-facing MCP server.
- Hardware requirements for tree-sitter graph servers at estate scale (millions of nodes) are not documented beyond the 219k-node VS Code run.
