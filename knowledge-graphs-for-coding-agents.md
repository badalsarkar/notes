# Layered context outperforms a single knowledge graph

Teams that run coding agents well on large codebases do not store engineering knowledge in one "technology knowledge graph". They build a layered context system in which each kind of knowledge sits in the store that suits it and reaches the agent through a matching channel. Short, human-written rules files (AGENTS.md, CLAUDE.md, Cursor rules) carry non-obvious conventions. On-demand skills carry procedures. MCP servers expose live sources such as code intelligence, service catalogs, tickets and documentation. Deterministic gates (permission settings, hooks, scanners and CI) enforce what must never be left to the model. For codebase knowledge at the scale of about 1 million lines, the evidence favours hybrids that combine agentic grep-style search with precise symbol indexes and, for multi-hop dependency questions, a code graph. Semantic vector search helps mainly on large repositories where the query wording does not match the code. The independent evidence is thinner than the marketing suggests. Controlled 2026 studies found that repository context files do not reliably raise task success and can add about 20% to cost ([Gloaguen et al.](https://arxiv.org/abs/2602.11988)), and long-context benchmarks show accuracy falling as more context is added ([Chroma](https://www.trychroma.com/research/context-rot)). Most of the large gains that vendors report (Augment's 70%+, Qodo's 80% on its own benchmark, Bito's 47% token reduction) are vendor-run and unreplicated. For a capital markets firm the practical consequence is that the engineering effort should go into a permission-aware, auditable context layer behind a gateway, with small curated instruction files, precise code navigation, enforced security gates and an internal evaluation suite, rather than into a single graph database.

## Knowledge reaches agents through four channels rather than one graph

The question of how to "feed technology knowledge to an agent" breaks down into five kinds of knowledge with very different properties. Tech standards and conventions are small, slow-changing and must apply almost everywhere. Security policies are partly guidance and partly hard constraints. Architecture knowledge (service boundaries, ownership, API contracts, decision records) changes at the pace of design decisions and lives in catalogs and documents. Codebase knowledge for a million lines changes with every merge and is far too large to place in a prompt. Organizational knowledge (why a decision was made, which ticket motivated a change) is scattered across tickets, pull requests and chat. Every major vendor has converged on the same small set of channels for delivering these: always-loaded instruction files, scoped or on-demand instructions (path-scoped rules and Agent Skills), tool access through MCP servers, and deterministic enforcement outside the model ([Claude Code memory docs](https://code.claude.com/docs/en/memory); [agentskills.io](https://agentskills.io/); [Cursor rules](https://cursor.com/docs/context/rules)).

The enterprise case studies show what a "knowledge graph" means in practice. Uber's agents reach source code, engineering docs, Slack and JIRA through a shared context layer and an MCP gateway, and run in sandboxed DevPods ([Pragmatic Engineer](https://newsletter.pragmaticengineer.com/p/how-uber-uses-ai-for-development)). Stripe's Minions run in isolated environments and mix deterministic steps such as lint, test and CI with agentic steps ([InfoQ](https://infoq.com/news/2026/03/stripe-autonomous-coding-agents/)). Neither is a single graph database. The graph is better understood as a federation of indexes that the agent can traverse through tools. My synthesis is that the federation works when its parts share stable identifiers (repository path, symbol identifier, service identifier in the catalog, ADR number, ticket key), because those identifiers are what let an agent hop from a ticket to a service to a symbol to its callers.

| Knowledge type | Typical size and change rate | Best store | Delivery channel | Freshness mechanism |
|---|---|---|---|---|
| Tech standards and conventions | Small, changes quarterly | Canonical standards repository | Org-level and repository instruction files | Human review, audit tooling such as `/doctor prompt-audit` |
| Procedures (how to add a report field, run a migration) | Medium, changes with tooling | Skill folders with scripts and references | Agent Skills loaded on demand | Versioned with the tooling they describe |
| Security policy | Small rules, large standards | Policy-as-code, scanner rulesets, permission settings | Hooks, permission deny lists, in-loop scanning, CI gates | Ruleset releases |
| Architecture (services, owners, APIs, ADRs) | Medium, changes with design decisions | Service catalog, ADR folder, OpenAPI/AsyncAPI specs | MCP server or live file references | Catalog is the system of record |
| Codebase (1M LOC) | Large, changes every merge | Search index, symbol index, optional embeddings and code graph | Agent tools (grep, symbol lookup, graph queries) via MCP | Incremental re-indexing on changed files |
| Organizational history | Very large, unstructured | Ticketing, wiki, chat, PR history | Permission-trimmed MCP search | Source systems remain authoritative |

## Five retrieval families compete to represent a million lines of code

Codebase knowledge is the hardest layer, and production systems use five families of technique: agentic lexical search, embedding retrieval, compressed repository maps, precise symbol indexes, and code or knowledge graphs. The main difference between them is when the work is done. Indexes pay their cost up front and need a freshness pipeline, while agentic search pays at query time in latency and tokens. By 2026 most serious systems are hybrids. Cursor states that grep and semantic search together give its best results ([Cursor](https://cursor.com/blog/semsearch)), and Sourcegraph describes a retrieve-then-rank pipeline that combines keyword search, embeddings and graph analysis ([Sourcegraph](https://www.plushcap.com/content/sourcegraph/blog/sourcegraph-lessons-from-building-ai-coding-assistants-context-retrieval-and-evaluation)).

The worked examples below use a hypothetical 1M-LOC post-trade platform made up of a Java trade settlement core, Kotlin and Python services for reference data and the counterparty hierarchy, a client mandate and restriction rules engine, a trade surveillance service, a regulatory reporting pipeline fed from Kafka topics, and a residue of SQL stored procedures and KDB+/q analytics.

### Agentic search reads the live tree at query time

**How it works.** The agent holds lightweight identifiers such as file paths and search patterns and loads content at runtime with grep, glob and file reads, without any pre-built index ([Anthropic](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents)). Claude Code's team reportedly started with a local vector database and switched to agentic search because it worked better, citing staleness and security concerns, though Boris Cherny described the evidence as "mostly vibes" plus some internal benchmarks ([OfficeChai](https://officechai.com/ai/claude-researcher-explains-how-agentic-search-performed-better-than-rag-for-code-generation/)). Cognition's SWE-grep is a variant in which a small model trained with reinforcement learning issues up to eight parallel grep and read calls per turn for at most four turns, and returns file and line lists rather than summaries ([Cognition](https://cognition.com/blog/swe-grep)).

**Strengths.** Results are always current, nothing needs to be deployed, and no second copy of the code leaves the machine. Exact strings such as error codes, configuration keys and class names are found reliably. Sourcegraph reports that well-tuned lexical ranking (BM25F, which ranks file names and symbol definitions above comments) improved relevance by about 20% and held up against embeddings in its internal evaluations ([Sourcegraph](https://www.plushcap.com/content/sourcegraph/blog/sourcegraph-keeping-it-boring-and-relevant-with-bm25f)).

**Weaknesses.** Cognition measured that agent trajectories in Windsurf and Devin often spent over 60% of the first turn retrieving context, and describes serial agentic search as slow and prone to flooding the context with irrelevant tokens ([Cognition](https://cognition.com/blog/swe-grep)). Grep cannot find code whose vocabulary differs from the question, and it follows cross-service edges only when names happen to match textually. A third-party analysis notes that index-free search can be slow on repositories with thousands of folders ([fast.io](https://fast.io/resources/how-cline-reads-files-without-indexing/)).

**Cost and operational burden.** The infrastructure cost is close to zero, but the token and latency cost grows with codebase size and question complexity. No public figures exist for Claude Code's token use on large repositories.

**Worked example.** Agentic search fits a production incident in the settlement core where the logs show `SSI_MISMATCH` on a failed instruction, because the error code is a literal string that leads directly to the validator and its tests. It does not fit the question "where do we compute the contractual settlement date for T+1 markets?" when the code variously uses `valueDate`, `sd`, `contractualSettle` and a calendar service with a different name, because the agent must guess the vocabulary across a million lines and will spend many turns doing so.

### Embedding retrieval finds code by meaning

**How it works.** Code is split into chunks, embedded, and stored in a vector index that the agent queries in natural language. Cursor trains its own embedding model on agent session traces so that similarity scores match what an LLM judged most helpful at each step ([Cursor](https://cursor.com/blog/semsearch)). Greptile argues that natural-language queries and raw code do not land near each other in embedding space, so it generates docstrings per AST node and embeds those instead ([Greptile](https://www.greptile.com/blog/semantic-codebase-search)).

**Strengths.** Embedding retrieval handles vocabulary mismatch, which is the case grep handles worst. Cursor reports that semantic search raised offline accuracy by 12.5% on average (6.5% to 23.5% by model) on its internal benchmark, and that in an online A/B test code retention rose 0.3% overall and 2.6% on codebases with more than 1,000 files ([Cursor](https://cursor.com/blog/semsearch)). The gain is concentrated in large repositories, which is the relevant case for 1M LOC.

**Weaknesses.** Chunking can separate logic that belongs together, an index is a snapshot that drifts with every merge, and embeddings are a second copy of sensitive intellectual property ([Cline](https://cline.bot/blog/why-cline-doesnt-index-your-codebase-and-why-thats-a-good-thing)). Cognition notes that embedding search is inaccurate on multi-hop questions and can inject irrelevant content that the agent overweights ([Cognition](https://cognition.com/blog/swe-grep)). Sourcegraph removed embeddings from Cody Enterprise in favour of search, citing scale and the wish not to send code to a third-party embedding API ([Sourcegraph Cody FAQ](https://sourcegraph.com/docs/cody/faq)). Cline's arguments against indexing contain no measurements, so the dispute is between operational risk on one side and vendor-measured accuracy on the other.

**Cost and operational burden.** Embedding computation, a vector store, a sync pipeline, and in a regulated firm a data-residency review of the embedding model. Cursor's index is unusable until 80% is built, and large repositories historically took hours to index before its index-reuse work ([Cursor](https://cursor.com/blog/secure-codebase-indexing)).

**Worked example.** Embedding retrieval fits the T+1 settlement-date question above, because "settlement date calculation for T+1" lands near the relevant code even when the names differ. It does not fit the question "which services call `CounterpartyHierarchy.getUltimateParent()` and would break if it returned an empty optional?", because similarity search returns code that looks related rather than the exact set of callers, and a missed caller in a credit-exposure aggregation path is a correctness problem rather than a ranking problem.

### Repository maps give orientation within a fixed token budget

**How it works.** Aider uses tree-sitter to extract where symbols are defined and referenced, builds a file graph, ranks it with PageRank personalised toward the files being edited, and emits a compact text map within a token budget that defaults to 1,000 tokens ([Aider](https://aider.chat/2023/10/22/repomap.html)). An analysis of the source gives the budget formula as max(1024, min(max_input_tokens/8, 4096)) ([hermes-agent issue #535](https://github.com/NousResearch/hermes-agent/issues/535)).

**Strengths.** It needs no external service or embeddings, is cheap to compute, and tells the model which files and symbols are central.

**Weaknesses.** The map deliberately omits most symbols. A budget of 1,000 to 4,000 tokens cannot meaningfully represent a million lines, so at that scale the map serves as orientation rather than retrieval.

**Cost and operational burden.** Low, limited to tree-sitter parsing on each run.

**Worked example.** A repository map fits a 30,000-line trade surveillance alert-enrichment service, where a 4,000-token map can name the main detectors, enrichers and their dependencies. It does not fit the whole post-trade monolith, where the map would keep only the most-referenced utility classes (logging, money, date helpers) and hide the business logic the agent actually needs.

### Precise symbol indexes answer definition and reference questions exactly

**How it works.** A per-language indexer, usually driven by the build, records every definition and reference. Sourcegraph's SCIP replaced LSIF partly because SCIP can re-index only changed files ([Sourcegraph](https://sourcegraph.com/blog/announcing-scip)). Meta's Glean stores facts in RocksDB, targets incremental cost proportional to the change, answers simple declaration lookups in about a millisecond, and follows cross-language edges across Thrift RPC and FFI ([Meta Engineering](https://engineering.fb.com/2024/12/19/developer-tools/glean-open-source-code-indexing/)). Serena gets the same precision from live language servers across more than 40 languages ([rywalker.com](https://rywalker.com/research/serena)), and Moderne's Lossless Semantic Tree adds full type attribution by invoking the repository's real Gradle or Maven build ([Moderne](https://docs.moderne.io/user-documentation/agent-tools/mcp/overview/)).

**Strengths.** This is the only family that gives exact, compiler-accurate answers to "where is this defined" and "who calls this", and it supports safe, deterministic refactoring. Glean shows that the approach scales to Meta's monorepo.

**Weaknesses.** It needs an indexer per language and often a working build, and it covers code only. Kythe's reliance on a unified build system such as Bazel is a known constraint for codebases without one ([Hacker News comment](https://hn.jakechampion.name/item/30854916)). Languages without a mature indexer, such as q or vendor SQL dialects, are left to text search.

**Cost and operational burden.** This is the highest setup cost of the code-only options, because indexing must run in CI for each language and the build must be reproducible. Sourcegraph's MCP server is reported as Enterprise and sales-gated ([wal.sh survey](https://wal.sh/research/2026-code-graph-mcp-survey/)), while Serena is MIT-licensed but runs language servers on the developer machine.

**Worked example.** A symbol index fits a change to the mandate engine's `isRestricted(account, instrument)` signature in a Gradle-built Java and Kotlin monorepo, because it returns every call site, including those in the pre-trade compliance check and the end-of-day breach report, and Moderne-style tooling can apply the change deterministically. It does not fit the KDB+/q tick analytics or the stored procedures that populate the reporting warehouse, because no indexer covers them and the agent falls back to grep there.

### Code graphs follow multi-hop and hidden dependencies

**How it works.** A graph of files, classes, functions and their containment, import, call and inheritance edges is built, usually with tree-sitter, and exposed to the agent as traversal or query tools. Research systems include RepoGraph (line-level dependency graph, ICLR 2025) ([arXiv 2410.14684](https://arxiv.org/abs/2410.14684)), LocAgent (heterogeneous graph with traversal tools) ([arXiv 2503.09089](https://arxiv.org/abs/2503.09089)), KGCompass (links issues and PRs to code entities) ([arXiv 2503.21710](https://arxiv.org/abs/2503.21710)) and CodeCompass (dependency graph served over MCP) ([arXiv 2602.20048](https://arxiv.org/abs/2602.20048)). Open-source MCP servers such as code-graph-rag (Memgraph), CodeGraphContext (Neo4j) and codebase-memory-mcp (single binary, 158 languages) package the same idea ([wal.sh survey](https://wal.sh/research/2026-code-graph-mcp-survey/)).

**Strengths.** The academic evidence for graphs is the strongest of any family, although it is on small Python repositories. KGCompass reports that 69.7% of successfully localized bugs required multi-hop graph traversal, and reaches 58.3% repair on SWE-bench Lite in its journal version ([KGCompass](https://arxiv.org/abs/2503.21710)). LocAgent reports up to 92.7% file-level localization with a fine-tuned 32B open model ([LocAgent](https://arxiv.org/pdf/2503.09089)). On hidden-dependency tasks, CodeCompass reports 99.4% completion with graph navigation against 76.2% for a vanilla agent and 78.2% for BM25 retrieval ([CodeCompass](https://arxiv.org/abs/2602.20048)). Tool authors report large token savings for structural queries, such as about 3,400 tokens through a graph versus about 412,000 through grep and reading for five queries, but the methodology was not published ([dev.to CodeGraph review](https://dev.to/andrew-ooo/codegraph-review-pre-indexed-knowledge-graph-for-ai-agents-af1)).

**Weaknesses.** Tree-sitter resolves names syntactically, so calls through dependency injection, overloads, reflection and dynamic dispatch are approximate or missing. Reviewers report that some graph tools become noisy on polyglot repositories, generated code and large monorepos ([shiporskip.io](https://shiporskip.io/compare/claude-context-zilliztech-mcp-codebase-search-claude-code-2026-vs-gitnexus-zero-server-code-knowledge-graph-browser-rag-2026)). The most important limitation is behavioural: in CodeCompass, 58% of trials that had graph access made zero calls to the graph tool, and agents needed explicit prompting to use it ([CodeCompass](https://arxiv.org/abs/2602.20048)). The author calls this the "navigation paradox". Using an LLM to extract the graph, as Microsoft GraphRAG does, is reported to cost about 1,000 times a vector index to build (about $1,544 versus about $1.45 per million tokens) and historically required full re-indexing ([beri.net](https://www.beri.net/article/graphrag-vs-vector-rag-indexing-query-cost-lightrag-lazygraphrag-2026)), which makes it a poor primary index for code that a parser can read exactly.

**Cost and operational burden.** The range is wide. A single static binary is light, while Neo4j or Memgraph-backed tools add a database server and embedding infrastructure. Licensing also varies: GitNexus is PolyForm Noncommercial and therefore unusable commercially without a licence ([wal.sh survey](https://wal.sh/research/2026-code-graph-mcp-survey/)), and the embedded graph database Kuzu was archived in October 2025 after Apple acquired it ([The Register](https://www.theregister.com/2025/10/14/kuzudb_abandoned/)).

**Worked example.** A code graph fits the question "if we change how trade enrichment populates `executionVenue`, which MiFIR transaction report fields change?", because the path runs from the enrichment service through a Kafka topic schema to a reporting mapper, and a graph that links producers, topics and consumers makes the multi-hop path explicit. It does not fit a single-hop string lookup, where a graph adds a service to operate without improving the answer, or a Spring application whose wiring is mostly in configuration and annotations that a tree-sitter graph cannot resolve.

### Side-by-side comparison of the retrieval families

| Family | Best question type | Main strength | Main weakness | Operational burden | Freshness | Evidence quality |
|---|---|---|---|---|---|---|
| Agentic search (grep, glob, read; SWE-grep) | Exact strings, recent edits | Always current, no data copy | Many turns and tokens, misses vocabulary mismatch | Very low infrastructure, high token cost | Live | Qualitative (Anthropic), vendor-internal (Cognition) |
| Embedding retrieval | Concept search in large repos | Handles vocabulary mismatch | Weak on exact relations, second copy of IP | Medium to high (embeddings, store, sync) | Minutes (Cursor syncs changed files) | Vendor A/B (Cursor), vendor eval (Augment) |
| Repository map | Orientation in small or medium repos | Cheap, no service | Cannot represent 1M LOC | Low | Recomputed per run | Design documentation only |
| Precise symbol index (SCIP, Glean, LSP, LST) | Definitions, references, impact, refactoring | Compiler-accurate and fast | Per-language indexers, build dependency, code only | High (CI indexing per language) | Incremental on changed files | Industrial use at Meta and Sourcegraph, no agent benchmark |
| Code graph (tree-sitter or research graphs) | Multi-hop and hidden dependencies | Strong academic localization gains | Approximate resolution, agents underuse it | Low to high depending on backend | Varies, often batch | Peer-reviewed but small Python repos |

## Rules files advise the agent while hooks and CI gates enforce policy

Standards, security policies and architecture reach the agent through four mechanisms, and the most important design decision is which of them is advisory and which is binding. Anthropic's documentation states that CLAUDE.md content is "context, not enforced configuration", and that blocking a tool, command or path belongs in managed permission settings or a PreToolUse hook ([Claude Code memory docs](https://code.claude.com/docs/en/memory)). That distinction applies equally to every vendor.

### Instruction files carry short conventions that apply everywhere

**How it works.** A Markdown file is loaded into every session, layered from organization to user to repository to directory. AGENTS.md is the cross-vendor baseline and has been governed by the Linux Foundation's Agentic AI Foundation since December 2025 ([agents.md](https://agents.md/); [OpenAI](https://openai.com/blog/agentic-ai-foundation)). The nearest file to the edited code wins, and Codex concatenates files root to leaf until a default limit of 32 KiB, beyond which content is silently dropped ([Codex docs](https://learn.chatgpt.com/docs/agent-configuration/agents-md)). Claude Code supports a managed CLAUDE.md distributed by MDM or Ansible that developers cannot exclude, path-scoped `.claude/rules/` files, and symlinks to a shared standards repository ([Claude Code memory docs](https://code.claude.com/docs/en/memory)). Cursor team rules can be enforced from a dashboard ([Cursor](https://cursor.com/docs/context/rules)), and Copilot organization instructions apply on GitHub.com surfaces only ([GitHub docs](https://docs.github.com/en/copilot/reference/custom-instructions-support)).

**Strengths.** Agents do follow these files. In the ETH Zurich study, a tool mentioned in the file (`uv`) was used 1.6 times per task, against fewer than 0.01 times when it was not mentioned ([Gloaguen et al. v3](https://arxiv.org/html/2602.11988v3)). The format is portable across almost every agent, so a firm can write its standards once.

**Weaknesses.** The files are advisory, cost tokens on every call, and lose adherence as they grow. Vendors recommend under 200 lines per CLAUDE.md and under 500 lines per Cursor rule ([Claude Code](https://code.claude.com/docs/en/memory); [Cursor](https://cursor.com/docs/context/rules)). The IFScale benchmark found the best frontier models at about 68% accuracy with 500 simultaneous instructions, with omissions as the main failure ([arXiv 2507.11538](https://arxiv.org/abs/2507.11538)). The controlled studies are discussed in the evaluation section below, and their headline is that codebase overviews in these files did not help agents find the right files. Anthropic warns that contradictory instructions may be resolved arbitrarily ([Claude Code memory docs](https://code.claude.com/docs/en/memory)).

**Cost and operational burden.** Low to write but continuous to maintain. Each file is a document that must be reviewed when the underlying standard changes, and generators such as agentsmesh compile one canonical rule set into each vendor's format ([agentsmesh](https://samplexbro.github.io/agentsmesh/canonical-config/rules/)).

**Worked example.** An instruction file fits conventions like "represent monetary amounts with the firm's `Money` type and never with `double`", "use the shared `BusinessDayCalendar` for settlement dates", and "run `./gradlew check` before proposing a change", because these are short, non-obvious and apply across the settlement and reporting code. It does not fit an attempt to paste the firm's 300-page secure coding standard or the full list of client mandate restrictions into the file, because the length will reduce adherence, the content will be truncated or ignored, and the restriction data belongs in the rules engine rather than in a prompt.

### Agent Skills package procedures that load on demand

**How it works.** A skill is a folder with a `SKILL.md` file (name and description frontmatter) plus optional scripts and reference files. Only the name and description load at start-up, the full instructions load when a task matches, and bundled files load during execution ([agentskills.io](https://agentskills.io/)). Anthropic released the format as an open standard, and aggregators report support in more than 30 tools by April 2026 ([noqta.tn](https://noqta.tn/en/news/skill-md-open-standard-30-ai-coding-tools-adoption-2026)).

**Strengths.** Standing context cost is small, so a firm can publish many procedures without bloating every prompt. Scripts inside a skill let the agent run a deterministic step instead of improvising.

**Weaknesses.** Loading depends on the model deciding that the skill applies, so a skill is the wrong place for a constraint that must always hold. No controlled study of skills on coding outcomes was found in the research.

**Cost and operational burden.** Moderate, since each skill is a small versioned package that must track the tooling it wraps.

**Worked example.** A skill fits "add a new field to the EMIR trade report", which involves a schema change, a mapping, a golden-file regression test and a sign-off checklist, and which is needed a few times a quarter. It does not fit "never write client account numbers or LEIs to application logs", because that rule must apply on every change and cannot depend on the agent choosing to load a skill.

### MCP servers deliver live architecture and organizational knowledge

**How it works.** An MCP server exposes tools and data that the agent calls at runtime. Backstage ships an MCP actions backend that exposes catalog actions as MCP tools ([Backstage](https://backstage.io/docs/ai/mcp-actions)). Context7 serves version-specific library documentation ([GitHub upstash/context7](https://github.com/upstash/context7)). Community ADR servers query decision records and claim to detect drift from code, though they have small user bases ([glama](https://glama.ai/mcp/servers/tosin2013/mcp-adr-analysis-server)). Kiro steering files can embed live workspace files such as an OpenAPI spec through `#[[file:path]]` references, which is a file-based alternative that avoids copy drift ([Kiro docs](https://kiro.dev/docs/steering/)).

**Strengths.** The source system remains authoritative, so the agent sees current ownership, API contracts and decisions without anyone copying them into a rules file.

**Weaknesses.** Each server is a new attack and permission surface. Backstage's Actions Registry does not enforce permissions automatically, so each action handler must check authorization itself, and the registry is marked alpha ([Backstage](https://backstage.io/docs/next/backend-system/core-services/actions-registry)). Agents also have to choose to call the tool, which the CodeCompass result shows is not guaranteed.

**Cost and operational burden.** Moderate to high, covering hosting, authentication, scoping tokens per task, and auditing calls.

**Worked example.** An MCP server fits "who owns the counterparty hierarchy service, what is its current API version, and which ADR decided that ultimate-parent resolution is cached for 24 hours?", because the catalog and ADR folder answer this authoritatively and the answer changes over time. It does not fit a rarely changing convention such as the logging format, where a one-line rule is cheaper than a tool round trip.

### Enforcement gates make policy binding

**How it works.** Managed permission deny lists and sandbox settings block commands and paths, PreToolUse hooks run code before an action regardless of what the model decides ([Claude Code memory docs](https://code.claude.com/docs/en/memory)), in-loop scanners such as Semgrep Guardian scan each file the agent writes and return findings ([Semgrep Guardian](https://docs.semgrep.dev/guardian)), and CI gates reject non-compliant pull requests.

**Strengths.** These are the only mechanisms that hold when the model ignores guidance, and the security evidence shows that guidance alone is insufficient. Veracode found vulnerabilities in 45% of AI-generated outputs across more than 100 models, with Java failing 72% of the time (vendor) ([Veracode](https://www.veracode.com/resources/genai-code-security-report/)). Security-aware prompting reduced vulnerabilities by up to 56% for GPT-4o in one study ([Bruni et al.](https://alphaxiv.org/overview/2502.06039v1)), which is a large reduction but not elimination.

**Weaknesses.** Gates can only enforce what can be expressed as a rule or a scanner signature. Semgrep Guardian does not block code, and its hosted Claude Code and Codex plugins use a fixed ruleset rather than organization policies ([Semgrep Guardian](https://docs.semgrep.dev/guardian)), so a hard guarantee still needs a blocking CI check.

**Cost and operational burden.** Moderate. Most firms already run SAST, SCA and secrets scanning in CI, and the extra work is moving the same checks into the agent loop so that the agent fixes problems before a human sees them.

**Worked example.** A gate fits "no hard-coded credentials, no dependencies outside the approved artifact repository, no writes to production configuration paths, and no use of deprecated cryptography", because each is mechanically checkable. It does not fit "netting logic belongs in the settlement bounded context rather than the reporting service", which is an architectural judgment that needs a reviewer or an ADR-aware review agent.

| Mechanism | Binding or advisory | Standing context cost | Best for | Main risk | Maintenance owner |
|---|---|---|---|---|---|
| Instruction files (AGENTS.md, CLAUDE.md, rules) | Advisory | Paid on every call | Short, non-obvious conventions | Bloat, contradiction, silent truncation | Platform team for org layer, domain teams for directories |
| Agent Skills | Advisory, loaded on demand | Near zero until used | Multi-step procedures | Not loaded when needed | Owners of the wrapped tooling |
| MCP servers | Advisory content, live source | Tool definitions only | Architecture, catalog, tickets, docs, code intelligence | Injection and over-broad tokens | Owners of the source system plus gateway team |
| Hooks, permissions, scanners, CI | Binding | None | Security and compliance constraints | Only covers what is expressible as a rule | Security engineering |

## Commercial context engines split into code-structure and organizational camps

The research found no product that offers an open, temporal knowledge graph joining precise code symbols with tickets, pull requests and ADRs. Commercial vendors claim parts of this, so a firm that wants the whole picture today either combines a code-structure engine with an organizational engine behind one gateway or builds the join itself.

## Most performance numbers are vendor-reported and untested at 1M LOC

The evidence base has three tiers, and a decision-maker should weight them very differently. Peer-reviewed or preprint studies are controlled but run mostly on Python repositories far smaller than a million lines. Vendor-run evaluations are larger and closer to production but are not independently replicated and often use the vendor's own benchmark. Practitioner and aggregator claims are the weakest and sometimes conflict with each other. No study found in this research compares retrieval approaches in a controlled way at 1M+ LOC, and no peer-reviewed benchmark uses repositories at that scale.

| Claim | Figure | Source type | Caveat |
|---|---|---|---|

Two patterns stand out when the tiers are read together. First, the anti-index position (Anthropic, Cline) rests on operational arguments about freshness and intellectual-property copies, while the pro-index position (Cursor, Augment) rests on vendor accuracy numbers that grow with repository size. These positions measure different things and are not in direct conflict. Second, Cursor's own data shows the average benefit of semantic search is small (+0.3% retention) and the benefit on large repositories is larger (+2.6%), which is consistent with grep being adequate for small and medium repositories and insufficient for vocabulary-mismatch queries in large ones ([Cursor](https://cursor.com/blog/semsearch)). For a 1M-LOC estate, the honest conclusion is that each firm needs its own evaluation, because the public data cannot settle the question at that scale.

## Accuracy falls as context grows so maintenance matters more than volume

The case for careful context curation rests on independent evidence that models get worse as context grows, even well below their advertised window sizes. Chroma tested 18 models and found that performance degraded with input length in every experiment, that a single semantically similar distractor lowered accuracy, and that focused prompts of about 300 tokens beat full prompts of about 113,000 tokens on LongMemEval for every model ([Chroma](https://www.trychroma.com/research/context-rot)). NoLiMa found that on its hard subset, where the answer requires a non-literal association, Llama 3.3 70B fell from 98.3 to 8.9 at 32,000 tokens ([NoLiMa](https://arxiv.org/html/2502.05167v3)). "Lost in the Middle" found that models do worst when the relevant document sits in the middle of the context ([Liu et al.](https://arxiv.org/abs/2307.03172v3)), although Chroma did not observe a position effect on its simpler task with newer models. For code, the distractor finding is the most relevant, because a large codebase is full of similar functions, deprecated versions of the same API and copy-pasted variants, and each one placed in context next to the correct code lowers accuracy.

Agent builders respond with a common set of context-maintenance techniques. Anthropic describes just-in-time retrieval, compaction that summarises a long session and keeps the five most recently accessed files, tool-result clearing, structured notes written outside the window, and sub-agents that explore with tens of thousands of tokens and return 1,000 to 2,000-token summaries ([Anthropic](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents)). Manus adds that the KV-cache hit rate is its most important production metric, because cached input costs a tenth of uncached input and input outweighs output about 100 to 1 ([Manus](https://manus.im/blog/Context-Engineering-for-AI-Agents-Lessons-from-Building-Manus)). These two pieces of advice pull against each other, since compaction and clearing rewrite history and break the cache, and neither vendor publishes effect sizes on coding benchmarks. Cognition argues for a single agent with shared context, because decisions taken inside one sub-agent are invisible to parallel agents and lead to inconsistent results ([Cognition](https://cognition.com/blog/dont-build-multi-agents)). That disagreement remains open.

Keeping knowledge fresh is a separate problem from fitting it into the window. Cursor publishes the most concrete mechanism: a Merkle tree of file hashes, about 3.2 MB for a 50,000-file workspace, identifies changed branches, changed files are re-chunked, embeddings are cached by chunk content, and a new clone reuses a teammate's index when their trees are similar. Clones within an organization average 92% similarity, and the 99th-percentile time to first query fell from 4.03 hours to 21 seconds ([Cursor](https://cursor.com/blog/secure-codebase-indexing)). The same hashes act as an access control, since the server drops results for files the client cannot prove it holds. SCIP and Glean apply the same principle to symbol indexes by re-indexing only what changed ([Sourcegraph](https://sourcegraph.com/blog/announcing-scip); [Meta](https://engineering.fb.com/2024/12/19/developer-tools/glean-open-source-code-indexing/)). Generated prose has no equivalent. An OpenWrt maintainer reported that DeepWiki pages were not regenerated after the repository changed and described configuration options incorrectly ([OpenWrt forum](https://forum.openwrt.org/t/important-consideration-deepwiki-ai-generated-docs-may-contain-inaccuracies/249471)), and a community plugin had to add its own drift check because the generator it forked "only generates, never detects drift" ([driftwiki](https://www.remoteopenclaw.com/plugins/dpviivqb-driftwiki/driftwiki)). Claude Code's `/doctor prompt-audit` checks instruction files for references to files or commands that no longer exist and for contradictions between files ([Claude Code memory docs](https://code.claude.com/docs/en/memory)), which is the closest thing to a drift check for rules.

The evaluation evidence on context files is the most useful guide for what to put in them. In Gloaguen et al., LLM-generated context files reduced resolution by about 0.5 points on SWE-bench Lite and about 2 points on the new CTXbench, developer-written files gave a non-significant +2.4 points, and both added steps and roughly 19 to 23% cost. Codebase overviews appeared in nearly every generated file and did not reduce the steps needed to reach the files the reference patch changed. The authors recommend omitting LLM-generated files and limiting human-written files to non-obvious requirements ([Gloaguen et al. v3](https://arxiv.org/html/2602.11988v3)). The v1 abstract stated that the files "tend to reduce" success, and the wording was softened in later versions ([arXiv v1](https://arxiv.org/abs/2602.11988v1)). Khatri's 291-run study on merged PRs found no effect from either always-on or selective context files, with a minimum detectable effect above 30 points, and attributed the remaining failures to implementation skill such as architectural choice and exact wiring rather than missing repository knowledge ([Khatri](https://arxiv.org/html/2607.27250v1)). Lulla et al. found a 28.64% lower median runtime and 16.58% fewer output tokens with AGENTS.md at comparable completion ([Lulla et al.](https://arxiv.org/abs/2601.20404)), which conflicts with Gloaguen's cost finding because the two studies measure different things. The defensible reading is that short human-written files change agent behaviour in targeted ways, that general overviews cost tokens without improving navigation, and that the effects are small enough that a firm must measure them on its own tasks.

## Persistent context opens supply-chain and injection risks

Every persistent context source is a place an attacker can write to, and every retrieval source is a place an attacker can inject instructions. Pillar Security showed that hidden instructions in Cursor and Copilot rules files, using invisible Unicode characters, could make the agent insert malicious scripts and hide the change from the developer, that poisoned rules persist across future sessions and forks, and that they can spread through shared rule repositories ([Pillar Security](https://pillar.security/blog/new-vulnerability-in-github-copilot-and-cursor-how-hackers-can-weaponize-code-agents)). Cursor and GitHub responded that reviewing output is the user's responsibility. Invariant Labs showed that a malicious public GitHub issue could hijack an agent using the official GitHub MCP server into leaking private repository data into a public pull request, with no server bug involved, only prompt injection and a broadly scoped token ([Invariant Labs](https://invariantlabs.ai/blog/mcp-github-vulnerability)). Simon Willison is quoted as saying that convincing mitigations do not yet exist ([DevClass](https://devclass.com/2025/05/27/researchers-warn-of-prompt-injection-vulnerability-in-github-mcp-with-no-obvious-fix/)), and the concrete mitigations documented are least-privilege, per-repository tokens and limiting the agent to content from trusted authors ([Docker](https://www.docker.com/blog/mcp-horror-stories-github-prompt-injection/)).

Hallucinated dependencies are the other major supply-chain risk, and they are predictable enough to exploit. Spracklen et al. generated 576,000 code samples across 16 models and found that 19.7% of recommended packages did not exist, that open-source models hallucinated far more than commercial ones (21.7% against about 5.2%), and that 43% of hallucinated names recurred on every re-run of the same prompt ([Socket](https://socket.dev/blog/slopsquatting-how-ai-hallucinations-are-fueling-a-new-class-of-supply-chain-attacks)). Attackers can therefore pre-register those names. Endor Labs reports that 34% of suggested dependency versions were hallucinated and that giving agents tools improved dependency safety threefold (vendor) ([Endor Labs](https://www.endorlabs.com/learn/prompt-patterns-that-make-coding-agents-write-safer-code)). In a bank that already resolves dependencies through an internal artifact repository, a registry existence check against that repository in the agent loop is a cheap and effective control.

Regulated firms add requirements that most public material does not address for coding agents specifically. The banks with public accounts built their tools in-house on licensed models rather than sending code to unmanaged services ([American Banker](https://www.americanbanker.com/news/morgan-stanleys-michael-pizzi-is-27-on-the-most-innovative-people-in-finance-ranking); [Reuters via Yahoo](https://finance.yahoo.com/news/jpmorgan-engineers-efficiency-jumps-much-190410471.html)). Vendor commentary stresses immutable audit logs, residency inside the firm's tenancy, and the absence of audit-rights clauses in many frontier-model API terms ([Diagrid](https://www.diagrid.io/infrastructure/2026-compliance-checklist-ai-agents-banking); [Sardine](https://www.sardine.ai/blog/agentic-ai-in-banking)). Several vendor blogs report that the April 2026 interagency guidance SR 26-2 superseded SR 11-7 and placed generative and agentic AI outside formal model-risk scope ([Arthur.ai](https://www.arthur.ai/column/ai-agent-compliance-tools-for-banks-a-guide)), but the primary text was not checked in this research, so a firm should confirm this with its model risk function before relying on it. If the report is accurate, coding agents would fall under existing SDLC, change-management and third-party risk controls, which makes audit trails of what context the agent saw and what it changed even more important.

## Banks and big tech build federated context layers behind gateways

The enterprises with detailed public accounts share an architecture, and the largest gains come from bounded transformation work rather than general coding. Morgan Stanley's in-house DevGen.AI produces plain-English specifications from legacy code. It reviewed about 9 million lines in its first five months, saving an estimated 280,000 developer hours across about 15,000 developers, and reached about 16 million lines by February 2026 (company-reported) ([TMCnet summary of WSJ](https://blog.tmcnet.com/blog/rich-tehrani/ai/morgan-stanley-uses-ai-to-translate-cobol.html); [American Banker](https://www.americanbanker.com/news/morgan-stanleys-michael-pizzi-is-27-on-the-most-innovative-people-in-finance-ranking)). The bank said fully automated translation was not yet mature. JPMorgan's CIO reported 10 to 20% productivity gains for tens of thousands of engineers using an internal assistant ([Reuters via Yahoo](https://finance.yahoo.com/news/jpmorgan-engineers-efficiency-jumps-much-190410471.html)). Goldman Sachs began a supervised pilot of Devin alongside about 12,000 developers in 2025 ([eWeek](https://www.eweek.com/news/goldman-sachs-ai-coding-agent-devin/)), and its productivity figures were not traced to a primary disclosure. Nubank used Devin to split a monolith of more than 6 million lines, with Cognition reporting an 8 to 12 times gain in engineering hours (vendor case study) ([Devin](https://devin.ai/customers)).

Outside finance, the pattern is similar. Stripe's Minions reportedly produce about 1,300 merged PRs a week with humans reviewing every change ([InfoQ](https://infoq.com/news/2026/03/stripe-autonomous-coding-agents/)). Google's CEO said about 75% of new Google code was AI-generated and approved by engineers in April 2026 ([Semafor](https://www.semafor.com/article/04/24/2026/google-ceo-says-75-of-companys-new-code-is-ai-generated)). A counter-example is instructive: Uber migrated about 75,000 test classes from JUnit 4 to 5 with OpenRewrite and evaluated and rejected generative AI for that task because its output was inconsistent ([daily.dev](https://app.daily.dev/posts/uber-migrates-75-000-test-classes-from-junit-4-to-junit-5-using-automated-code-transformation-vnaof82ob)). Deterministic tools still win mechanical transformations, and the right design gives the agent access to them rather than asking it to imitate them.

Legacy modernization is where explicit knowledge graphs for code are most mature as products, which matters for banks with COBOL settlement and ledger systems. AWS Transform for mainframe builds a knowledge graph from code, data and activity analysis, added a traceable workflow from business-rule extraction to code generation in June 2026, and AWS documents feeding its output to Claude Code ([AWS](https://aws.amazon.com/about-aws/whats-new/2026/06/aws-transform-mainframe-traceable-reimagine-workflow/); [AWS blog](https://aws.amazon.com/blogs/migration-and-modernization/reimagining-mainframe-applications-with-aws-transform-and-claude-code/)). The convergent pattern is a static structural graph, LLM-generated specifications attached to graph nodes, and that enriched graph used as agent context. Practitioners stress that COBOL experts are still needed to define the transformations ([ITPro](https://www.itpro.com/software/development/you-need-those-experts-to-even-define-what-these-transformations-are-cobol-developers-will-always-be-needed-even-as-ai-takes-the-lead-on-modernization-projects)).

The broader trends point in one direction. DORA 2025 found AI use at 90% of about 5,000 respondents and concluded that AI amplifies the existing strengths and weaknesses of an organization, with loosely coupled architectures and AI-accessible internal data among the capabilities that determine benefit ([Google Cloud](https://cloud.google.com/blog/products/ai-machine-learning/announcing-the-2025-dora-report)). Trust is falling: in Stack Overflow's 2025 survey distrust of AI accuracy rose to 46% and only about 33% trusted AI output ([InfoWorld](https://infoworld.com/article/4031673/ai-use-among-software-developers-grows-but-trust-remains-an-issue-stack-overflow-survey.html)). Standards are consolidating under neutral governance. The Agentic AI Foundation launched in December 2025 with MCP, AGENTS.md and goose as founding projects and Bloomberg as a Platinum member ([SiliconANGLE](https://siliconangle.com/2025/12/09/linux-foundation-announces-agentic-ai-foundation-joined-anthropic-openai-block/)), and a secondary source reports that Wells Fargo and Visa joined later ([Latent Space wiki](https://latent.space/wiki/aaif/)). Adoption of context files is growing from a low base, with an academic sample finding only about 5% of repositories using any format in late 2025 ([arXiv 2510.21413](https://arxiv.org/html/2510.21413v1)). The practical effect of standardization is that a firm can build one internal context layer (AGENTS.md for static instructions, Skills for procedures, MCP for live access, a gateway for policy) and serve it to several vendors' agents, which reduces lock-in at a time when banks are buying from more than one vendor.

## A reference architecture for a 1M-LOC capital markets estate

The recommendation follows from the evidence above. Put binding constraints outside the model, keep always-loaded instructions short, give the agent precise and fresh code navigation, expose architecture and history through permission-aware tools behind a gateway, and measure every layer on the firm's own tasks. The architecture below is my synthesis for a firm with about 1 million lines across a post-trade platform, a mandate rules engine, a surveillance service and a reporting pipeline. Each layer names what it holds, the recommended technology, and the limitation to plan for.

| Layer | What it holds | Recommended implementation | Limitation to plan for |
|---|---|---|---|
| 0. Enforcement | Security and compliance constraints that must always hold | Managed permission deny lists and sandboxing, PreToolUse hooks, secrets scanning, SAST and SCA in the agent loop and as blocking CI gates, dependency resolution only through the internal artifact repository, invisible-Unicode checks on instruction files | Only covers rules that can be expressed mechanically |
| 1. Org and repo instructions | Non-obvious conventions, build and test commands | One canonical AGENTS.md in a standards repository, compiled to vendor formats, distributed through managed org layers, under about 200 lines, CODEOWNERS on every instruction file | Advisory, decays with length, must be reviewed when standards change |
| 2. Scoped rules and skills | Domain conventions and procedures | Path-scoped rules per bounded context (settlement, reference data, reporting, surveillance), Skills for multi-step procedures with deterministic scripts | Skills load only when the agent judges them relevant |
| 3. Code intelligence | The 1M-LOC codebase | Agentic search as the baseline, a precise symbol index (SCIP via Sourcegraph, or LSP via Serena) for Java, Kotlin, Python and TypeScript, Moderne-style LST tooling for large refactors, a service dependency graph built from build files and interface definitions (Avro, Protobuf, OpenAPI), generated code excluded, a self-hosted semantic index only if evaluation shows a gain | Per-language indexer and build maintenance, no coverage for q or vendor SQL |
| 4. Architecture | Services, owners, API contracts, ADRs, data classification | Service catalog (Backstage) as system of record exposed through MCP with per-action authorization, ADRs in repositories with structured identifiers, API specs referenced live rather than copied | Catalog quality determines answer quality |
| 5. Organizational history | Tickets, PRs, design docs, decisions | Permission-trimmed MCP search over Jira and Confluence or an organizational engine, an optional temporal graph for decision history treated as an experiment | Unstructured sources are injection surfaces |
| Gateway and audit | Policy, identity, logging | An MCP gateway (agentgateway or equivalent) with per-task scoped tokens, permission-aware retrieval inherited from source systems, immutable logs of every retrieval and tool call | Adds latency and a component to operate |
| Evaluation | Evidence that each layer helps | An internal task suite built from the firm's own merged PRs, run with and without each layer, tracking pass rate, cost, turns and post-merge defects | Requires sustained engineering time to keep representative |

Three design choices deserve emphasis. The first is to make identifiers the join keys of the "graph". If the catalog uses the same service identifier that appears in build files and Kafka topic ownership, if ADRs reference those identifiers, and if tickets carry them, then an agent can traverse from a ticket to a service to its symbols and callers using ordinary tools, without a central graph database. A dedicated graph store is worth adding when the firm's own evaluation shows that multi-hop questions are frequent and that the agent uses the graph tool when prompted, since the CodeCompass result shows that availability alone does not produce use. The second is to treat instruction files as code. They should go through review, have owners, be scanned for hidden characters, and be checked in CI for references to files and commands that no longer exist, because both the drift evidence and the Pillar attack show that unreviewed persistent context fails silently. The third is to scope access per task. The Invariant result shows that a broad token plus untrusted content is enough to leak a private repository, so an agent working on the surveillance service should receive a token that reaches the surveillance repository, the catalog and the relevant Jira project, not the whole estate.

A worked example shows how the layers combine. A developer asks an agent to add a new restriction type to the client mandate engine that blocks a client from trading instruments issued by entities within its own counterparty hierarchy. Layer 1 tells the agent to use the `Money` type and to run the engine's golden-file tests. Layer 2 loads the "add a restriction type" skill, which includes the schema migration script and the regression checklist. Layer 4 tells the agent through the catalog that the counterparty hierarchy service owns ultimate-parent resolution, that its current API is v3, and that an ADR requires callers to tolerate a 24-hour cache. Layer 3 returns every caller of the existing restriction interface, including the end-of-day breach report the developer had not mentioned. Layer 0 rejects a first draft that pulls an unapproved graph-traversal library and logs LEIs at debug level. The audit log records which catalog entries and ADRs the agent read, which supports a later model-risk or change-management review. The same architecture does not help with the judgment of whether self-issuer restrictions should live in the mandate engine at all or in a pre-trade compliance service, which is the kind of design decision Khatri's study found static context does not fix ([Khatri](https://arxiv.org/html/2607.27250v1)), and which stays with an architect.

A phased rollout reduces the risk of building layers that do not help.

| Phase | Scope | Exit criterion |
|---|---|---|
| 1. Baseline and guardrails (first 6 to 8 weeks) | Layer 0 gates, a short canonical AGENTS.md, a 50 to 100 task internal evaluation suite from recent merged PRs, the MCP gateway with audit logging | Baseline pass rate and cost measured, gates blocking in CI |
| 2. Precise navigation (next quarter) | SCIP or LSP indexing in CI for the main languages, service dependency graph from IDL and build files, catalog MCP with per-action authorization | Measured gain on cross-service tasks over the baseline |
| 3. Selective enrichment (following quarter) | Skills for the most frequent procedures, path-scoped domain rules, optional semantic index or commercial context engine evaluated head to head, organizational history via permission-trimmed MCP | Each addition kept only if it improves pass rate or cost on the suite |
| 4. Modernization tracks (as needed) | Legacy specification extraction for COBOL or SAS components, Moderne-style deterministic refactors, traceability from extracted rule to generated code | Specifications reviewed by domain experts before code generation |

The build-or-buy decision depends on data-residency constraints more than on features. A firm that can approve a vendor's remote indexing can evaluate Augment, Qodo or Bito against Sourcegraph on its own suite. A firm that requires air-gapped or in-tenancy deployment should favour self-hostable options (Sourcegraph, Qodo on-prem, Tabnine with its acquisition risk, Moderne CLI, Serena) and accept the integration work that comes with them. In either case the firm should own Layers 0, 1, the gateway and the evaluation suite itself, because those encode its standards and risk posture and are the parts that make any vendor's engine replaceable.

## Conclusion

The idea of a single "technology knowledge graph" that an agent consults is useful as a mental model and misleading as an implementation plan. The systems that work are federations: deterministic gates for what must hold, a few hundred lines of carefully chosen instructions, precise code navigation that stays fresh through incremental indexing, and permission-aware tools over the systems of record for architecture and history. The research changes the emphasis of the question from "how do we give the agent more knowledge" to "how do we give the agent less but more exact knowledge, at the moment it needs it, through channels we can audit". The independent studies on context files and long-context accuracy both show that extra context has a real cost, while the graph studies show that exact structural information helps most on the multi-hop, cross-service problems that dominate a large post-trade estate.

For a capital markets firm the decisive factors are not model capability but governance and measurement. The strongest public results in banking come from bounded understanding and transformation work with humans in the loop, and the weakest evidence concerns general productivity claims and vendor benchmarks at a scale nobody has tested independently. A firm that builds its own evaluation suite from its own merged changes, scopes every agent token to the task, and treats instruction files and MCP servers as reviewed, owned code will be able to adopt or replace vendors on evidence. A firm that skips those steps will be relying on vendor numbers that, as of late 2026, no one has replicated at 1M lines of code.
